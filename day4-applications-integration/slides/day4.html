Module 1

Requirements

Exam watch

One sentence → two lists

Infrastructure requirements sit on four axes: latency (measured from the user's region) · scale (peak volume) · residency (where data is processed / which regulation) · identity (credential model + audit trail).

"Help agents respond faster" is a business problem, not a requirement. Requirements are derived from it, are verifiable, and trace back to a regulation or a stakeholder — and they become your eval criteria + design constraints. Every stem in this skill asks you to sort or derive one list.

Module 2

Systems life cycle

Exam watch

Four stages — "implement" means deploy

"Implement" ≠ write the code. Who deploys → implement. Who gets the 2 a.m. call → operate. When it's retired → maintain.

The guide's fuller arc: Requirements → Design → Build → Test → Deploy → Operate → Iterate, with gates — residency clears Design; a new model version passes the eval baseline before Deploy. Build the eval suite during Build — it gates deploys and validates every later change. Claude apps need continuous monitoring: model behaviour can shift on a version bump, prompts drift with usage.

Module 3

Software-engineering foundations

Concept

What turns code into a service anyone owns

  • Version control — remembers every change → rollback is picking the last good version, not reconstructing it.
  • Code review — a second engineer reads every change → knowledge stops living in one head.
  • Pipeline — branch → review → test → deploy. Shipping becomes a route, not an event on a laptop.
  • Refactoring — improve shape without changing behaviour. Small (rename/tidy) & large (restructure). Only safe once history + tests exist.
  • REST / JSON / async you already have from Day 1.

Rule 2 lives here too: "requires that any engineer can roll back" kills "write a setup doc" — a doc is guidance; VCS + pipeline is the mechanism.

Module 4

Application design & configuration management

Exam watch

Where Claude sits = which contract applies

A scenario that describes where Claude sits in a system is really asking which contract applies. Choose by latency requirement; the cost follows.

Guide · D2
Concept

Application design = requirements before code

  • What interface — chat / API endpoint / background job? What latency budget?
  • What failure behaviour — the model WILL sometimes return something unusable. A production design says what then: validation · retries with backoff · a fallback path · human escalation.
  • SW-eng foundations back it: idempotency · logging · separate the prompt layer from business logic.
  • Output shape — prose for a human, a schema for a dashboard. Session hygiene — one session per task (clear / compact / inspect).

Application design is the single biggest D2 sub-skill — worth more than Claude Code + Debugging combined.

Exam watch · Claude Application Design · D2 (8.6%)

Where the model runs — and what that rules out

first-party Claude API  ·  Claude Platform on AWS  ·  Amazon Bedrock (Messages API)  ·  Bedrock legacy  ·  Google Vertex AI  ·  third-party (e.g. Microsoft Foundry)

  • Choice follows the customer's cloud + compliance posture, not the developer's familiarity. Measure on three: latency (from the customer's actual region, actual payload) · compliance (pass/fail at scoping) · total cost per call (tokens + egress + integration).
  • Regulated-data routes decide endpoint / credentials / log destination before any prompt or tool is designed:
  • Direct API has no EU residency → route via Bedrock/Vertex with the region pinned. HIPAA BAA excludes Console / Workbench / beta / consumer. FedRAMP only via C4G / Bedrock GovCloud / Vertex Assured Workloads. Managed Agents — not ZDR / HIPAA-BAA eligible.
  • A strict system prompt is not a residency or compliance control.

Exam watch

A prompt edit IS a deployment

  • API keys — environment variables or a secrets manager. Never in code, never in the client. Key in a mobile app? → a backend proxy, no exceptions.
  • Prompts are versioned artifacts — changed deliberately, tested before rollout. A prompt edit ships to production; treat it like one.
  • Model choice is configuration too — pinned and intentional, so an upgrade is a decision with a test pass, not a surprise.

Configuration Management is ~4% on its own — the guide quietly telling you it shows up.

Module 7

Evaluation

Exam watch

Assert on structure, not wording

Output wording varies by design — test the contract. Introduce a regression (drop the citation instruction) → tests go red, each naming the case + failed check.

Grading method is a decision tree: one exact label → string match · structured output → a code-graded check · open-ended quality → LLM-as-judge (calibrate against human labels first). Judge technique: ask for strengths / weaknesses / reasoning before the score, or it drifts to a safe ~6. The golden set runs on every prompt or model change.

Lab · eval harness + regression

A 12-case eval set for the RAG answerer · 3 checks (structural / keyword / LLM-judge) wired as pytest · then break it and watch ≥ 3 tests fail.
