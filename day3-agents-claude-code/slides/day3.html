Module 1

Should you build an agent?

Concept

Workflow vs agent — who decides the path?

  • Workflow — your code decides the path, in a structure you designed.
  • Agent — the model decides the path: calls tools in a loop, observes results, chooses next, until it's done.
  • The exam's favourite question isn't "can you build an agent" — it's "should you". Simplest structure that solves the task.

Predictable steps, known sequence → workflow, every time (cheaper, faster, debuggable, testable). Open-ended, path can't be scripted → agent, paying for it in cost + latency + a harder test story.

Guide · 7:51 · D1
Concept

Five workflow patterns (your code, the path)

  • Prompt chaining — one step's output feeds the next.
  • Routing — a cheap first call classifies, then sends the request down the right branch.
  • Parallelisation — fan out, then aggregate.
  • Orchestrator–workers — one model plans, others execute.
  • Evaluator–optimiser — one model generates, another critiques, in a loop.

Reaching for an agent when a three-step chain would do is the overbuild in its natural habitat.

Concept

Four checks + the loop guardrails

Should you build an agent? All yes:

  • Complexity — multi-step, hard to specify up front?
  • Value — justifies the cost + latency?
  • Viability — is Claude good at this task type?
  • Cost of error — caught & recovered (tests, review, rollback)?

The agent loop, in production, needs:

  • a cap on iterations
  • timeouts
  • a defined way to fail

Agent spinning forever / burning budget? The answer is loop limits + a termination condition — not a second agent to supervise the first.

Module 3

Hooks — code the model can't talk out of

Exam watch

The hook lifecycle

  • A blocking PreToolUse hook is the mechanism answer to a must / never security stem.
  • Exit code 2 blocks. Exit code 1 only warns — the frequent "the hook didn't actually stop it" bug. A code-2 deny short-circuits the loop even under bypassPermissions.
  • Also fires: UserPromptSubmit · SubagentStart/Stop. Hooks run in-process, zero context cost, synchronously — keep them < ~500 ms.
  • PostToolUse tags fetched external text as untrusted, reformats results. Stop reads the transcript — a review can't END until a comment was posted.

Concept

A blocking hook, in code

async def block_refund(input_data, tool_use_id, context):
    if input_data["tool_name"] != "refund": return {}
    return {"hookSpecificOutput": {"permissionDecision": "deny",
        "permissionDecisionReason": "refunds require human approval"}}

Runs before the tool. Returns a decision. The model's intent doesn't matter — the code decides.

Module 4

Subagents — usually fewer

Concept

Coordinator fans out

Usually fewer agents. Each one adds context, latency, cost. A single loop is easier to debug and eval. Fan out only when the work truly parallelises or one loop would fill its context with reading.

Anthropic's own multi-agent research system runs at ~15× the token cost of a single-agent chat — worth it only when the task genuinely splits into independent parallel parts. On tightly-coupled work (coding) subagents mostly wait on each other. The three axes a subagent buys: context isolation · parallelisation · specialisation.

Exam watch · Claude Code Operation · D3

settings.json precedence — and the one exception

managed  >  CLI flags  >  local (.claude/settings.local.json, gitignored)  >  project (.claude/settings.json, checked in)  >  user (~/.claude/settings.json)

  • Exception: permissions (allow / deny / ask) accumulate across every scope — they don't follow override precedence. Deny always beats allow, at every mode and scope.
  • Six permission modes — a risk decision, not convenience: default · plan · acceptEdits · auto (classifier-reviewed) · dontAsk (allow-list only) · bypassPermissions (isolated environments only — uniquely skips the protected-path guard).
  • CLAUDE.md fails by dilution, not by being wrong — a correct rule buried in 300 lines gets less attention. Scope the rest into .claude/rules/*.md with a paths glob.

Module 6

MCP

Exam watch

An MCP server is not a bag of tools

  • MCP is a protocol, not a library — Claude Code, Desktop, Cursor all speak it.
  • Build an MCP server when a capability should be shared & reused across apps/teams. Keep a plain in-process tool when it's specific to one app.
  • A remote server exposes dozens of tools — scope allowed_tools. Least privilege: an agent that only needs to read should not hold a tool that writes.
  • Secrets via ${ENV_VAR} expansion — never hardcoded. A plugin runs code with your privileges — a trust decision.

Four ways to extend an agent — pick one

MechanismReach for it when…
Built-in toola generic, already-available capability — file I/O, shell, web
Custom toolone app, one specific function, no reuse elsewhere
Skilla repeatable process / judgement call — no new live data
MCP servermultiple apps need the same live/dynamic data or action, maintained independently
  • "MCP connects Claude to data; Skills teach Claude what to do with it." A production agent usually uses all of them together.
  • Scenario needs fresh or external data → it's a tool or an MCP, never a Skill.
  • MCP tool schemas are deferred by default — loaded on demand, so they don't cost context until used.
