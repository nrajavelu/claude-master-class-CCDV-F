Prompt engineering

  • Contract (role · rules · output shape) → system. Task + data → messages. If you'd paste it every turn, it's a system prompt.
  • Chain-of-Thought — zero-shot ("think step by step") / structured (name the steps) / few-shot. Helps maths & multi-constraint choice; skip for classify/extract. "CoT always helps" is a distractor. See reasoning-patterns.md.
  • Structure inputs with tags (<ticket>, <doc>) — instruction ≠ data, and first line of injection defence.
  • Two prompts both correct → the exam prefers the shorter one with a concrete example.

The three surfaces

  • Chat product — Anthropic's own system prompt sits under yours → prototype behaves great, doesn't transfer to the API.
  • Coding-tool rules file — arrives as a user message; later messages sit at the same level.
  • The API — instructions go in the top-level system field. No message has role:"system" (classic distractor).

Untrusted content — both directions

  • External / third-party content (a fetched page, a ticket) belongs in a tool_result block. ✓
  • Your own instructions never go in a tool_result — that channel is read with suspicion. ✗

Tools — the description is the interface

  • name (unique) · description (the biggest factor in correct use — say what, when, inputs) · input_schema.
  • Tool called at the wrong time? Check the description before the model.
  • Parallel tool_use → one user message, a list of tool_result blocks, ids matching.

Structured output you can trust

  • strict:true is a field on the tool definition; schema needs additionalProperties:false + everything in required.
  • No "optional" — optional = allow null as a type. Unsupported schema features are rejected, not ignored.
  • client.messages.parse() validates the response for you. Parse tool inputs with json.loads, never string-match.
  • On the SDK @tool path strict isn't forwarded yet — schema guides, validate() enforces. "Asking is not making sure."
