Module 0

How this exam is built

Exam method

Every question is one of four decisions

DecisionIt's really asking…Domains≈/53
① What runs?workflow vs agent · one loop vs sub-agents · built-in vs your tool vs plugged inD1, D8~13
② How does it call Claude?messages · stream vs batch · model tier · token costD2, D5~12
③ What does Claude see & say?context window · prompt build · output shape your code can consumeD6, D2, D3~13
④ Will it survive production?requirements & lifecycle · debugging · securityD2, D4, D7~15

Name the decision first — half the options belong to a different one. D2 is 33% of the exam; ~a quarter is plain software engineering with no Claude in it (that's Day 4).

Exam method

Two rules that kill wrong answers

Rule 1 — mechanism > knob

The stem names a constraint ("overnight", "cost is the concern"). The answer is the mechanism built for it (→ Batch). A generic dial — temperature, model tier, max_tokens, "raise the timeout" — is almost always a distractor.

Rule 2 — mechanism > guidance

If the stem says must / never / always / cannot, every option that is only advice ("tell the model to…", "write it down", "ask users to…") is dead. "A polite request is not an enforceable control." Only something that actually stops the bad case survives — isolation, a blocking hook, a schema.

Exam method

The four-step attack — on every item

  1. Name the decision (①–④). Wrong-decision options fall away.
  2. Find the constraint word — "overnight", "must never", "any engineer can roll back", "visible immediately".
  3. Apply Rule 1 / Rule 2 — kill the generic knobs; if there's a must/never, kill the guidance.
  4. Pick the mechanism that matches. Two options both work? Choose the cheaper / simpler / SDK-native one.

Module 1

Claude & the Messages API

Concept

The model family

  • Haiku — fastest, cheapest. High-volume, well-specified tasks: classify, extract, format.
  • Sonnet — balanced. Code, review, multi-step tool use.
  • Opus — deepest reasoning. Ambiguous, open-ended problems.
  • Newer generation numbers (4.5, 5, …) = smarter at the same tier.

Exam watch Default to the most capable model, then step down only when measurement says you can. Not "pick a tier by task type." (Day 5 goes deep.)

Our labs pin claude-haiku-4-5 — a classroom of keys, kept cheap.

Concept

One endpoint: /v1/messages

  • Everything goes through client.messages.create(...) (or .stream(...)).
  • Tools, images, PDFs, structured output, thinking — all are parameters of this one call, not separate APIs.
  • The API is stateless: you resend the whole conversation every turn. There is no "session" on the server.
import anthropic
client = anthropic.Anthropic()          # reads ANTHROPIC_API_KEY

resp = client.messages.create(
    model="claude-haiku-4-5",
    max_tokens=400,
    messages=[{"role": "user", "content": "Hello"}],
)
Concept

Anatomy of a request

fieldwhat it is
modelwhich model. An exact id string — claude-haiku-4-5.
max_tokenshard ceiling on the response. Hitting it truncates mid-thought.
systemthe durable instruction / role. Not a message — its own top-level field.
messagesthe conversation: a list of {"role": "user"|"assistant", "content": ...}.
tools, thinking, output_config …opt-in capabilities (Modules ahead / Day 2+).

First message must be user. content is a string, or a list of typed blocks.

Concept

Anatomy of a response

  • response.content is a list of blocks — text, thinking, tool_use… Always check block.type.
  • response.stop_reason — why generation stopped. You branch on this.
  • response.usage — input_tokens, output_tokens, cache counters. This is your bill.
  • You send dicts; you get back objects (dot access): response.usage.input_tokens.
text = "".join(b.text for b in response.content if b.type == "text")
Exam watch

valuemeaningyou do

Module 2

Prompt-engineering fundamentals

Concept

The system prompt is the steering wheel

  • Put the role, the rules, and the output shape here — it persists across every turn.
  • User messages carry the task and the data; the system prompt carries the contract.
  • Rule of thumb: if you'd repeat it every turn, it belongs in system.
system=(
  "You review Python for a teammate who will maintain it. "
  "One tight paragraph. No line-by-line. No praise."
)
Concept

Be explicit · structure · show don't tell

Be explicit

State the format, the length, the audience, what to exclude. Ambiguity is answered by the model guessing.

Structure with tags

Wrap inputs in <code>, <doc>, <transcript>. Claude reads structure well; it separates instruction from data.

Few-shot

One or two worked input → output examples beat a paragraph of description for format-following.

Concept

Steering the output shape

  • Say the shape in the system prompt: "Reply with exactly three bullets, no preamble."
  • Give a skeleton to fill in. Name the sections you want.
  • For guaranteed machine-readable output, that's structured outputs / strict tools — Day 2.
  • Prefill (putting words in Claude's mouth as the last assistant turn) is removed on current models — don't teach it.
Exam watch

Thinking & effort

  • Current models take thinking={"type": "adaptive"} — the model decides how much to think.
  • The old fixed budget_tokens is deprecated / rejected on current models. A classic stale-answer distractor.
  • output_config={"effort": "low|medium|high|xhigh|max"} dials overall thoroughness vs cost.
  • Reach for thinking on ambiguous, multi-step problems; skip it for classify/extract.
Drill · 15 min

  • Contract in system; task and data in messages.

Module 3

Streaming

Concept

Why stream

  • A non-streaming call holds the HTTP connection until the whole answer is done — big outputs can hit the request timeout and fail.
  • Streaming returns tokens as they're generated: no timeout risk, live UI.
  • Use the SDK helper — don't hand-assemble from events:
with client.messages.stream(model="claude-haiku-4-5", max_tokens=400,
                            messages=msgs) as stream:
    for chunk in stream.text_stream:
        print(chunk, end="", flush=True)
final = stream.get_final_message()   # full Message: usage, stop_reason, blocks

Module 4

Errors, retries, timeouts

Exam watch

Catch a chain, most-specific first

exceptionHTTPretry?
BadRequestError400no — your request is malformed
AuthenticationError401no — fix the key
PermissionDeniedError403no
NotFoundError404no — wrong model/endpoint
RateLimitError429yes — back off
APIStatusError≥500yes — back off
APIConnectionError—yes — network blip

A single except Exception throws away the retry / don't-retry distinction.

Concept

The SDK already does some of this

  • Built-in: retries 408 / 409 / 429 / 5xx + connection errors with exponential backoff. max_retries default 2.
  • Built-in: 10-minute default timeout; override per client or per request (client.with_options(timeout=30.0)).
  • Hand-roll a loop only when you need custom logic — honour retry-after, a wall-clock budget, structured logging.
  • refusal is not an exception — it's a stop_reason. Check it before reading content.

Module 5

Tokens, cost & the agentic loop

Concept

Count before you spend

  • client.messages.count_tokens(model=, system=, messages=, tools=) — a separate, cheap endpoint.
  • Use it to predict spend, or to check a prompt will fit the context window.
  • Cost = tokens × (price per million ÷ 1e6). Input and output are priced differently; output is dearer.
  • usage.cache_read_input_tokens ≈ 0.1× price — Day 5's caching lever.
counted = client.messages.count_tokens(model=M, system=S, messages=msgs)
est = counted.input_tokens * (1.00 / 1_000_000)   # Haiku input $/tok
Exam watch

The agentic loop · two rules

  1. After every response, append {"role": "assistant", "content": response.content} — the whole block list.
  2. If stop_reason == "tool_use": run each tool_use block, then append one user message whose content is a list of tool_result blocks, each with the matching tool_use_id.
user → assistant(tool_use) → user(tool_result) → assistant(text)  # end_turn

Loop until end_turn. Handle max_tokens / refusal. Cap the turns.
